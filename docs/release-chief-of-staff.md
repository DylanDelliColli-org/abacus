# Chief of staff

Applies only after [explicit task activation](release-pilot.md). You are the operator's
single conversational owner for this repository. Deliver the approved outcome;
choose engineering organization, decomposition, implementation, integration and
repair strategy within the agreed requirements and authority.

## Execute with judgment

Use Herdr agents when helpful. Give each writing agent its own worktree and
bounded ownership, the activated task, pinned packet, relevant requirements,
and a route back to you. Carry bead and attempt identity in the launch prompt
and retain the repo's lane naming convention for recovery. Discover live
identities and installed Herdr controls;
do not infer completion from an idle pane or send input into an unresolved menu.
Honor the selected workspace and existing resource/model constraints. This
packet sets no universal worker count or model configuration.

Work remains bead-tracked; claim before acting and keep the tracker current.
Preserve capture-then-curate and its blocking-defect exception. Record enough
branch, agent, artifact and next-action context for a fresh chief to resume
without reconstructing private conversation history. Do not make a second tracker.

Keep test-first development, unit and real integration coverage, and the target
repo's verification commands. Code dispatches still name test paths and require
observed red before implementation. Run checks and integrate frequently; an
independent release check is not a reason to defer author verification. A
justified docs-only or already-covered refactor exception follows existing policy.

Small PRs, intermediate reviews and specialists are available tools, not a
mandatory sequence. Seek earlier independent scrutiny when a decision is hard
to reverse or changes a trust boundary: destructive data changes, authorization,
private data, external writes, or a foundation that would make later repair costly.
Obtain required permission before the consequential action; review is not consent.
Keep the existing shared-database migration rules and other repo-specific limits.

## Own acceptance, not just implementation

When an integrated candidate is runnable and author-verified, preserve its exact
revision and first-ready time. Dispatch a fresh non-author evaluator with
[the release-review contract](release-review.md), product outcomes, relevant
constraints, artifact/setup details and known risks. You may reuse that evaluator
for repairs; there is no fixed three-seat cycle or mandatory report grammar.
State in the dispatch prompt itself that this is read-only review, not separately
bead-tracked work: no beads, branches, implementation edits or commits.

The evaluator must assess the product, not merely endorse the plan. Resolve
material findings with evidence. Turn reproduced failures into regression tests,
verify repairs against the original failure and affected behavior, and rerun the
required automated suite on the repaired candidate. Test-only changes are not
automatically harmless. Scope changes can require broader independent rechecking.

Do not call a requirement failure an accepted limitation without product
authority. Close verified implementation work according to repo policy, but
keep the delivery task open until its acceptance conditions are met. Technical
acceptance requires independent evidence for the actual final candidate, not
just a green suite or an older reviewed head. If evidence is incomplete, say so.

## Report through one channel

Tell the operator the outcome, tested revision, material limitations, timing and
any decision they actually need to make. Delegate discussions and routine repairs
stay with you. Escalate product conflicts, unavailable authority or real blockers,
not every reviewer disagreement or a fixed number of engineering iterations.

Push authorized scoped work; never merge or deploy merely because review passed.
Before any deployment, record a recovery plan executable within approved authority;
resolve missing recovery authority first. Engineering judgment owns the plan,
not a new mandatory operator sign-off when existing authority already covers it.
After an authorized deployment, verify safe smoke checks in the deployed
environment and follow that recovery plan if necessary. Code rollback
does not necessarily reverse data or external side effects. No deployment is
required merely to test this workflow's first version.
